# Production prerequisites configuration evidence

The production generator has an independent allowlist and requires explicit production inputs. It reads the checked-in local/review configuration only to deny known resource identifiers and origins. It never spreads review bindings, secrets, fixtures or organization data into production configuration. Unknown externally shared resources still require operator inventory verification; this generator cannot inspect their contents or prove account-wide isolation.

The generated worker is `judge-c2c-production`, with `judge-c2c-production-evaluator` and `judge-c2c-organization-production-evaluator` workflows. These names are separate from the credential-free native Workers Builds parent `judge-c2c`, its branch previews, and local/review workers and workflows. Production secrets must be provisioned only against `.wrangler/production.json` and `judge-c2c-production`; adding them to the native parent would expose privileged configuration to its preview deployment path. The production generator does not change the native parent or attach any production service/database binding to previews. Tests compare the generated worker/workflow names against every checked-in nonproduction configuration.

`PRODUCTION_RUNNER_MODE` defaults to `MANAGED`: a registry digest-pinned runner and custom domain remain required. The explicitly selected `OWNER_TUNNEL` profile accepts a `docker-local@sha256:<digest>` image and an HTTPS `trycloudflare.com` runner origin. Its production frontend may use only `judge-c2c-production.<CLOUDFLARE_WORKERS_SUBDOMAIN>.workers.dev`, with account subdomain explicitly supplied, workers.dev enabled and preview URLs disabled; it emits no custom-domain route for that hostname. Native parent, branch-preview and foreign-account hostnames are rejected. The owner's Mac, Docker daemon and tunnel must remain available; changing the tunnel requires updating the configured endpoint. This is an owner-operated execution profile, not managed availability or production event-scale capacity certification.

For KV-only owner deployment, leave `PRODUCTION_ARTIFACT_BUCKET` unset. The generator emits no R2 binding and requires a separate `PRODUCTION_ARTIFACT_KV_ID`; the existing artifact adapter uses KV without a new storage architecture. Managed deployment still requires its separate R2 bucket. A separate KV namespace establishes storage isolation; it does not bypass account quotas. Storage quota/rate-limit failures retain unavailable/failed artifact status and retry history rather than implying successful storage.

`tests/production-config.test.ts` verifies all eleven missing inputs fail before any config is written, known review D1/KV reuse is refused, the two production databases differ, origins are HTTPS and separate from review, runner endpoint differs from the judge origin, runner image is digest pinned, and secrets/review origin variables do not appear in the output. The generated worker has direct ORG_DB hosting and ORG_EVALUATOR; therefore it does not require ORG_SERVICE delegation. Both D1 databases are migrated by the gated production workflow. AI binding and provider/model are explicit; the signed runner endpoint is separately provisioned. `organizationEnv` preserves the configured environment, including production.

For custom-domain deployment, the generator declares the validated public hostname as an exact Cloudflare custom-domain route. Previously it disabled workers.dev and previews without declaring a public route. It rejects wildcard, IP, single-label, malformed, trailing-dot and nondefault-port public origins; workers.dev requires the explicit owner profile and exact separate production hostname described above. Managed HTTPS runner endpoints may use a separate port. The operator must own the Cloudflare zone and verify domain availability for custom-domain deployment. This follows [Cloudflare's custom-domain configuration](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

Focused verification on 2026-10-04: four production configuration tests passed, including route and invalid-origin regressions. Eight tests across `tests/reviewer-capacity.test.ts` and `tests/workflow-capacity-runtime.test.ts` passed in 46.81 seconds. They executed a 24-request burst across two real local Worker isolates sharing D1, crash expiry and stale-owner fencing, independent provider identities, real durable-engine exponential prepare backoff/recovery, supersession during provider work, and transient D1 evidence-write recovery. These are bounded local runtime results, not deployed multi-host event capacity. The configured provider lease intentionally permits one concurrent reviewer per provider per database; increasing it without a measured provider/runner capacity budget is not justified. Governance 01.12, 03.03 and 36.10 retain their production-runtime limitations.

Authenticated GitHub inspection on 2026-10-04 found only the `cloudflare-review` environment in `daksh1403/judge-c2c`; `cloudflare-production` was absent, and repository variable/secret name lists were empty. No secret values were read. Thus the production enablement flag, protected environment, eleven generator inputs and production credentials are actually missing from the configured production path.

The current `judge-c2c-daksh-codebase` organization installation has all-repository selection and grants `pull_requests:write`, `repository_hooks:write` and `workflows:write` beyond the source manifest's required contents/PR read and issues/checks write. Evaluation tokens are repository-scoped and explicitly downscoped, but the owner App grants still require reduction and renewed installation approval. A separate production App has not been established by this evidence. Least privilege 03.03 must remain PARTIAL until those owner-controlled grants and production installation are verified.

Before an explicitly authorized production deployment, the operator must:

1. Create fresh production DB and ORG_DB databases and KV namespace; managed deployment also requires a separate R2 bucket. Check account inventory to confirm none is used by local/review workers and start them empty; do not clone review data. Set protected `cloudflare-production` environment variables: `PRODUCTION_DATABASE_ID`, `PRODUCTION_ORG_DATABASE_ID`, `PRODUCTION_ARTIFACT_KV_ID`, `PUBLIC_ORIGIN`, `PRODUCTION_ORG_PUBLIC_ORIGIN` (same origin for direct hosting), and `PRODUCTION_ORG_NAME`. Set `PRODUCTION_ARTIFACT_BUCKET` for managed R2 deployment; leave it unset for the selected KV-only owner profile.
2. Provision a separate isolated signed runner host, its HTTPS endpoint, and digest-pinned image for the selected profile. Set `PRODUCTION_RUNNER_ENDPOINT` and `PRODUCTION_RUNNER_IMAGE`; set `PRODUCTION_RUNNER_MODE=OWNER_TUNNEL` for the owner Mac/tunnel profile and `CLOUDFLARE_WORKERS_SUBDOMAIN` when using its exact workers.dev frontend. Independently provision the same new runner signing secret as `RUNNER_TUNNEL_KEY` on the production worker and runner host; never reuse a review signing key. The generator does not attest runner reachability or execute participant code.
3. Select `PRODUCTION_AI_PROVIDER` (`cloudflare` or `callmissed`) and `PRODUCTION_AI_MODEL`. Provision a new production-only `CALLMISSED_API_KEY` when selecting callmissed. Provision new production-only `ORG_ADMIN_TOKEN`, `ORG_JUDGE_TOKEN`, `ORG_SECURITY_TOKEN` and a 64-hex-character `ORG_VAULT_KEY` through Wrangler secrets, never plaintext vars or checked-in files. Configure the separate production GitHub App through the authenticated organization connection flow; do not copy the encrypted review connection or private key. Provision public evaluator GitHub App/webhook/admin secrets separately if that API is enabled.
4. Generate and inspect `.wrangler/production.json`, apply migrations to both production databases, verify the exact configured production hostname, and deploy only after explicit authorization of the feature merge and protected production enablement. Custom-domain deployment requires an available Cloudflare zone; the owner workers.dev profile requires the configured account subdomain instead. Preview URLs remain disabled in both profiles. The existing workflow remains gated by `CLOUDFLARE_PRODUCTION_ENABLED` and a push to main.
5. Verify authenticated organizer/judge/security roles, GitHub App scope/webhook signatures, baseline/head runner execution, AI grounding, artifact retention, immutable retry history, and that previews cannot reach production resources or secrets.
