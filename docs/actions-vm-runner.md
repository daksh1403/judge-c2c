# Container-free GitHub Actions runner

The judge repository is public by owner authorization. Standard GitHub-hosted public-repository runners have free execution minutes; concurrency, storage and platform restrictions still apply. This adapter runs participant code in QEMU guest VMs, never directly on the Actions host. It is not enabled on production merely by adding the code.

## Trust boundary

Cloudflare snapshots exact immutable commits and creates a fresh D1 attempt before dispatching `evaluate.yml`. The Actions host claims that attempt using GitHub OIDC. The backend validates issuer/audience/signature/expiry plus repository ID, repository name, workflow path/ref/SHA, dispatch event, run ID and run attempt. The first claim fences all other Actions runs. Completion is single-assignment, request/result identities are checked, superseded work is rejected, and expired attempts remain in history. Retries create new attempts.

Participant files and one bounded operation enter a separate kernel/read-only guest disk. Guest Node commands run nonroot with minimal environment, dropped capabilities and CPU/process/file limits. The guest has 256 MiB memory, bounded tmpfs, no default route, QEMU restricted networking and no host mounts. Host HTTP assertions evaluate service responses. Assertions, callback identity and provider/App keys never enter the guest. Every supplemental command gets a fresh guest and original snapshot. Command results are supplemental; they cannot authorize functional PASS. No participant log/artifact is uploaded publicly by the runner.

The prepared disk, kernel and initrd are identified together as `qemu-vm@sha256:<digest>`. QEMU validates this composite digest before boot; Actions verifies the downloaded image as well. Changing a prepared environment requires new frozen contracts. Existing Docker/container contracts and history are retained.

## Preparation and activation

1. Review and merge the feature PR only with owner approval. GitHub requires a dispatchable workflow on the default branch. The PR's `Verify container-free VM` job prepares a frozen Debian/Node image and runs synthetic absence/reference/isolation checks on Linux. These are bounded tests, not event certification.
2. On disposable Linux, install `debootstrap debian-archive-keyring qemu-system-x86 e2fsprogs`, run `mkdir -p vm-runner/images`, then `sudo bash vm-runner/build-image.sh vm-runner/images`. Run `npm ci --ignore-scripts`, `npm run runner:vm:bundle`, and `VM_DISK=vm-runner/images/root.raw VM_KERNEL=vm-runner/images/kernel VM_INITRD=vm-runner/images/initrd npm run runner:vm:smoke`. Record the emitted image identity. Release only the tested disk/kernel/initrd from this build; never rebuild a tag under an existing contract.
3. Publish `root.raw.gz`, `kernel` and `initrd` as prepared release assets in the public runner repository. Set repository variables `RUNNER_VM_RELEASE` (exact release tag), `RUNNER_VM_IMAGE` (composite identity), and `RUNNER_JUDGE_ORIGIN` (exact permitted production origin). Image download and decompression affect job startup; measure this before the event.
4. Register a **separate runner GitHub App**, installed only on this runner repository, with Actions write and Contents read. Source/evaluation App credentials remain separate. Provision `RUNNER_APP_ID` and `RUNNER_APP_PRIVATE_KEY` only on the production Worker, never the public runner or guest. `RUNNER_INSTALLATION_ID` is nonsecret configuration.
5. Generate production config with `PRODUCTION_RUNNER_MODE=ACTIONS_VM`, `PRODUCTION_RUNNER_IMAGE`, `PRODUCTION_RUNNER_REPOSITORY`, `PRODUCTION_RUNNER_REPOSITORY_ID`, `PRODUCTION_RUNNER_REF`, `PRODUCTION_RUNNER_SHA` and `PRODUCTION_RUNNER_INSTALLATION_ID`. Ref/SHA must identify the exact organizer workflow commit. Do not update the pinned branch without updating and reviewing the operator configuration. The generator emits `RUNNER_ACTIONS_ORIGIN` equal to the production judge origin and no tunnel endpoint.
6. Apply migrations to DB and ORG_DB, deploy after authorized release, register new contracts with the VM image, and run the protected runner diagnostic. Verify actual authenticated dispatch → guest → evidence → GitHub check → frontend history. Existing attempts/contracts are not rewritten.

## Supported scope and remaining evidence

The initial VM profile inherits bounded Node source snapshots (100 files, 100 KB/file, 750 KB total). It supports trusted HTTP checks/benchmarks and bounded prepared Node/ESLint commands. Arbitrary framework/native/database/browser applications are not automatically supported. Offline dependency preparation is explicitly UNVERIFIED for this profile. Additional runtime profiles require prepared environments and evidence, rather than installing arbitrary packages on the host.

The trusted image is reproducibly catalogued from the fixed Debian snapshot with a pinned Node version and verified Node checksum. Image bytes are frozen by their actual digest; the build itself is not claimed bit-for-bit reproducible. Hosted QEMU binaries and Actions VM versions also vary and must be recorded/assessed during calibration. KVM is used when accessible; otherwise QEMU software emulation is slower. No 80-team capacity claim follows from a passing smoke test.

Before event activation: test guest escape attempts, process/output/disk exhaustion, detached processes, protocol spoofing, host/internal-network/metadata/Internet denial, wrong workflow identities, outage recovery, deadline bursts, cancellation and report retention. Rehearse 80 submissions and measure queue/boot/total latency. A 12-minute dispatch deadline deliberately records UNVERIFIED on unavailable capacity. The objective workflow allows up to 30 minutes for sequential baseline/head work. Secure public workflows can still have queues and provider rate limits.
