# Evaluation completeness contracts

These contracts preserve frozen inputs and expose provenance honestly. No participant receives backend/GitHub/AI credentials. All text remains escaped, logs redacted, and objective functionality without execution remains UNVERIFIED.

## Execution provenance

`GET /api/organization/evaluations/:id` retains `execution` records with `commit_sha`, `request_hash`, `result_hash`, `result` JSON and `created_at`, and optionally adds `origin_run_id`, `origin_execution_id`, `cache_key`, `cache_status` and `request` JSON. Cache status names: BYPASS, MISS, HIT (implementation may extend validated bounded reason codes). Cache identity scopes repository, exact commit, contract hash, complete runner policy, evaluator version, runtime/image/adapter/environment/resource settings and source snapshot hashes. Explicit cache policy NONE(default), BASELINE or ALL. Benchmarks bypass. Only structurally validated authenticated adapter results without missing/UNVERIFIED/timeout infrastructure evidence can be reused. Preserve original timing/request/run identity, revalidate current-head fences, and expose origin rather than pretending reuse is new execution.

## Protected artifacts

The same detail API retains `artifacts` with `key`, `run_id`, `sha256`, `bytes`, `content_type`, `created_at`, and adds `kind`, `storage` (R2 or KV), `status` (PENDING, STORED, FAILED, DELETED), `expires_at` and a bounded safe `error_code`. Content is redacted UTF-8 text/JSON, capped at 4 MiB per object and 20 MiB per run capture; no arbitrary binary execution or public URL. Keys are generated as `evaluations/:runId/:kind/:sha256`; kind is a controlled slug. Same-content retries are idempotent, preserve history, and do not overwrite original provenance.

`GET /api/organization/artifact?key=...` requires an authenticated judge/organizer session, scopes lookup to known run metadata and returns attachment/octet-stream, no-store, nosniff and `x-artifact-sha256` only after verifying actual bytes and hash. Unauthorized 401, unknown 404, expired/deleted 410, pending visibility or storage outage 503, integrity mismatch 502. Do not imply FAILED/PENDING artifacts are downloadable. KV's eventual consistency is handled as temporary unavailability, never successful empty content. R2 optional; isolated KV review namespace is fallback where billing prevents R2. Metadata remains in D1. Retention is explicit; historical digest/provenance remains after content expiry. Object-store failure cannot erase deterministic evidence or fabricate success.

Organizer-only `POST /api/organization/evaluations/:id/artifacts/retry` recomputes captures from preserved records; it does not re-evaluate or modify frozen inputs. Judge UI displays status/expiry, download only for STORED, and safe failure reasons. Artifact contents are evidence, never instructions.

## Judge detail presentation

UI must separate requirements, deterministic baseline/head results, AI interpretation, additional work and historical/current run status. Baseline failure is not automatically a participant regression. Cached results expose original run/times. Links use encoded known keys and existing application origin. Nonexistent optional fields remain explicitly unavailable; never fabricate coverage/security/performance output. Read-only judge operations remain usable; mutation controls require organizer authorization server-side.

## C00 clarifications (binding)

Execution row `result` stays a JSON-encoded string of the original validated result. `request` is a nullable JSON-encoded safe summary, not raw RunnerRequest: `{schemaVersion:1,runId,commit,contractHash,policyHash,timeoutSeconds,memoryMiB,files:[{path,sha256,bytes}]}`. File digests/bytes describe original source; no raw text. `request_hash` continues to describe the original complete authenticated request, never the redacted summary. Cache hits preserve `result.requestHash`, original `result.startedAt`/`finishedAt`, origin run/execution and result hash. A fresh lookup reconstructs and verifies identity using fresh frozen source and original request runId; any mismatch/corruption is a miss. Always persist redacted objective execution evidence with result_hash over the stored redacted bytes, preserving checks, statuses, timestamps and original request/run provenance. If redaction altered the authenticated payload, prohibit cache reuse, never discard useful objective evidence and never persist raw secrets. request_hash retains its original meaning. Null optional fields remain null; legacy absent fields are displayed unavailable. Provenance cache status on wire: BYPASS, MISS, HIT, with reason codes internal or separately exposed as bounded strings.

Detail API additionally returns `currentSubmission: {headSha:string,latestRunId:string,closed:boolean} | null` from the current submission record. Evaluation baseline/head inputs stay immutable. A matching current run requires matching ID and head and an open submission. No current record means unknown freshness, not latest.

Artifact timestamps `expires_at` are epoch milliseconds or null for legacy metadata. `created_at` is existing UTC database timestamp; no reinterpretation as a new execution time. Per-object expiry is fixed at initial allocation. Lifetime allocation across ALL metadata (including failed/deleted/expired) cannot exceed 20 MiB per run. Duplicate content/key consumes no additional allocation. Reserve quota atomically through conditional INSERT; verify stored allocation rather than assuming insert succeeded. Retry may only transition FAILED/PENDING to PENDING to STORED with conditional updates before expiry, never resurrect DELETED or expired rows. Up to five store attempts per object, reserved atomically. Append attempt history without altering original evidence. Cleanup uses durable DELETED tombstones; read authorization and tombstones precede backing-store reads. If concurrent cleanup defeats finalization, uploaded bytes remain inaccessible and are removed best-effort.

Retry accepts exactly `{}` and only for a terminal evaluation, otherwise 409. Missing evaluation 404; non-organizer 403; no configured object adapter 503. Success response: `{runId,status:'CAPTURED'|'PARTIAL',artifacts:[metadata],failures:[{kind,code}]}`. Failures are safe bounded codes, not external error strings. Artifact metadata fields are `key,run_id,sha256,bytes,content_type,created_at,kind,storage,status,expires_at,error_code` (error_code nullable). Download statuses remain 401/404/410/503/502 as above. Retry is a capture retry, never an evaluation mutation.

## Deterministic requirement projection

Evaluation detail also returns `requirementResults`, a projection of the frozen contract and objective evidence. Each entry contains `requirementId`, `mandatory`, `status` (PASS/PARTIAL/FAIL/UNVERIFIED), `needsAttention` and `criteria` (criterionId/status/evidenceIds/reason). Functional criteria require execution evidence; contradictory results retain failure. Partial completion never waives missing criteria. This projection does not award credit, replace AI observations or change completion policy.

Artifact cleanup uses internal upload/deletion tokens and fixed expiry. Expired downloads immediately return 410; physical cleanup retries durable pending work and revisits tombstones daily to cover crashes after late writes. This is eventual storage cleanup, not a claim of immediate provider deletion.

## Additional contribution review

A completed run exposes `additionalContributions`, distinct from mandatory requirement outcomes. Organizer-created immutable candidates select a frozen allowed category, exact changed paths, known evidence IDs and optional criterion IDs. A functional contribution needs objective execution PASS with baseline FAIL on the same criterion; other criteria use their authoritative verification kind. Unbound or insufficient evidence remains UNVERIFIED. Conflicting authoritative evidence cannot establish verification.

Organizer-only `POST /api/organization/evaluations/:runId/contributions` accepts `{category,title,description,paths,evidenceIds,criterionIds}`. At most 20 candidates per run are admitted atomically. `POST /api/organization/contributions/:candidateId/decisions` accepts `{decision,reason,requestId,expectedPreviousSequence}`; decision is RECOGNIZED or REJECTED, reason at least 20 characters, requestId UUID, and expectedPreviousSequence is the latest sequence or null for an initial decision. Replay is idempotent; stale conflicting reviews return 409. Decisions are append-only and audited. Recognition additionally requires verified evidence, the current exact completed open eligible submission, and no policy failure or participant regression. Neither action awards scores or changes mandatory criteria. Judges read; organizers decide.

## Operational timing and ordering

Submission order accepts only newest or oldest, with stable repository/PR tie-breakers. Overview timing summarizes at most 100 recent runs and 5,000 recorded transitions, with sample counts and truncation disclosure. Consecutive records in the same stage preserve its first timestamp. Completed intervals only are aggregated; running stages and missing timestamps remain unavailable. Observed wall time is not a resource or production-capacity measurement.
