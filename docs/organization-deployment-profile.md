# Organization deployment profile

The supported profile is one GitHub organization and one active event per independent Worker deployment. Each deployment configures its own `ORG_NAME`, `ORG_PUBLIC_ORIGIN`, `ORG_DB`, GitHub App connection, credentials and evaluation workflow. Organization evaluation queries use `ORG_DB`, and the App credential envelope authenticates `ORG_NAME`. The application does not provide organization switching within a shared deployment or shared-database tenant routing.

This profile can represent multiple organizations through independent deployments. It does not require a new shared multitenancy model. Event selection remains limited to `initial`: storing another event row does not make that event independently operational.

`tests/organization-isolation.test.ts` exercises two separately migrated D1 resources with colliding team/repository/submission IDs, resource-local sessions and App credential envelopes. A second regression starts two real local Worker isolates and invokes the organization router over HTTP. It verifies independent logins, rejection of the other deployment's cookie/access code/origin, organization-specific team reads, and a team mutation that leaves the other database unchanged. The test harness restores its fixture Origin header inside each isolate because Miniflare's host proxy restricts arbitrary Origin headers; the application origin and session checks remain in place.

Run `npx vitest run tests/organization-isolation.test.ts`. Both regressions pass with synthetic local organization data and no live GitHub calls. This is executed local runtime evidence, not a deployed Cloudflare or live GitHub multi-organization certification.

Production isolation requires distinct Worker/Workflow and database resources, independent App installations and secrets, independent artifact resources, and explicit runner/provider boundaries. Start each deployment from empty resources; do not copy review bindings, connection ciphertext, access codes or participant data. Verify both deployed frontends and webhooks, negative cross-session/artifact access, and independent execution before making a live multi-organization claim. The existing production prerequisites are in [current-production-prerequisites.md](qa/current-production-prerequisites.md).

Acceptance item 45.01 is titled “Organizations.” The deployment profile establishes the application capability to represent independent organizations. A LIVE_INTEGRATION claim about multiple deployed organizations still needs evidence from multiple independently configured deployments; one live organization plus these local regressions does not establish that claim. This change does not alter the acceptance ledger or claim concurrent event management.

An organization deployment has a persisted ACTIVE → RETIRING → RETIRED lifecycle. Organizer-authorized retirement removes the old App installation only after exact organization confirmation and replacement verification acknowledgement. The console accepts only the bounded credential-free receipt; the operator CLI additionally compares exact old and replacement resource identifiers and reverifies the replacement before authenticating at the old origin. See [organization-onboarding.md](organization-onboarding.md) for the explicit command and recovery flow.

RETIRING is already fenced and cannot return to ACTIVE following an uninstall outage. RETIRED retains immutable historical records and artifact access as a read-only archive. Registration, syncing, challenge configuration, contribution decisions, participant/security writes, evaluation retries and execution controls are absent in archived consoles for every role. Only an organizer can retry pending installation removal; the frozen replacement identity is preserved. Current status exposes replacement details only to organizers. Each replacement remains an independent empty deployment, without old team or repository data. Review deployments and browser tests use synthetic fixtures; these states do not establish live organization installation, provider availability or event capacity.
